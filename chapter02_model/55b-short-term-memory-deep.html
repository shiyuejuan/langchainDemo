55b · 短期记忆三脚凳 · 深度版（机制层）

55 课用“拆腿实验”证明了三者缺一不可。这里把内部机制扒开：每次 invoke 后台到底跑了什么、三种存储各存在哪、以及你最可能问的 8 个问题。

一、先纠正一个误解：State 不是“可拆的腿”，是凳面（必有的基底）

课程写“State + Checkpointer + Thread ID”，但严格说 State 是永远存在的——它是 LangGraph 图的状态表（TypedDict，含 messages + 你加的 user_name 等字段）。 没它图都跑不起来。

所以更准确的说法是：State 是“记忆的载体”，Checkpointer + Thread ID 是“让载体跨调用活下来”的两个条件。 拆掉后两者，State 每次都是新建的全新白板——也就是金鱼脑。

二、一次带 Checkpointer 的 invoke，后台到底干了啥（时间线）

① 接单：invoke(input, config={"thread_id":"t1"})
② 存档员去 t1 抽屉找快照：首次→空，从初始 state 开始；非首次→取出上次存的 state（消息+字段）铺回。
③ 合并输入：把 input 的 messages（追加）和 user_name（覆盖）写进 state。
④ 跑 agent 循环：model 节点→（工具节点）→model……每跑完一个“超级步”就存一份 checkpoint。
⑤ 收工：把最终 state 存回 t1 抽屉，return 整份 state。
🗄️ t1 抽屉此刻存着：messages（含两轮全部对话）+ user_name + 各节点执行进度
⑥ 下次 invoke(t1)：回到 ②，从抽屉取出 → 消息条数自动续上。

“拍照”是每步拍一次，不是只拍最后一张。Checkpointer 存的是 该 thread_id 的 state 快照 + 节点执行进度， 所以就算中途崩溃，也能从断点续跑——这才是它和“单纯把 messages 存文件”的本质区别。

三、为什么是“2 条 → 4 条”？（铁证拆解）

时刻t1 抽屉里有什么消息数
第 1 轮前空0
第 1 轮后[用户“我叫小测”, AI“你叫小测”]2
第 2 轮取回 + 新输入 + 新回复[旧2条, 用户“我叫什么”, AI“你叫小测”]4

“2→4”就是历史续上的硬证据：旧 2 条从抽屉里铺回来了。没有 checkpointer，每次都从 0 开始，永远停在 2。

四、三种“存”的精确分工（别再混）

组件存的是什么寻址方式存活范围在 47/48/55 哪讲过
State单次运行的全部字段（messages+自定义键）无（内存中的当前表）单次 invoke 内部47/50
Checkpointer某 thread_id 的 state 快照 + 进度thread_id跨 invoke（同线程内）45/55
Store跨会话的业务数据（用户画像/偏好）namespace 元组跨会话/跨用户47/48/53

一句话：Checkpointer 管“对话进行到哪了”，Store 管“某用户的某份资料”。两者都能持久，但粒度不同。 55 的三脚凳只负责“会话内续命”；真正跨天、跨进程的长期记忆，是 Store（或把 Checkpointer 换成 SqliteSaver 落盘）。

五、InMemorySaver 的“短期”到底多短？

InMemorySaver 把快照存在进程内存里。所以：

  • ✅ 同一次程序运行内、同 thread_id → 记得住（55 实验 0）；
  • ❌ 程序一关、再打开 → 抽屉清空，全忘（这就是为什么它叫“短期”）。

要“长期”就把 InMemorySaver() 换成 SqliteSaver.from_conn_string("mem.db")（落本地文件）， 或上 LangGraph Platform 的托管版——机制完全一样，只换“抽屉”的材质（内存↔磁盘）。

六、常见问题 8 连

Q1：thread_id 能用中文 / 任意字符串吗？ 能，它只是个标识，比如按“用户ID+日期”拼。

Q2：两个不同用户用同一个 thread_id 会怎样？ 串台——两人对话混在一起（45 课场景③的反面教训）。

Q3：怎么“清空记忆”？ 换一个 thread_id 即可；旧抽屉留着但不再读。要真删就调 checkpointer 的 delete 接口。

Q4：State 里我加的 user_name 会进快照吗？ 会！整个 state（含 user_name）都进 checkpoint。 所以 54 课里 user_name=明明 其实也躺在 t1 抽屉里，只是模型不自动读它（54 课核心）。

Q5：不给 thread_id 真的报错吗？ 真报错——55 实验 2 实测 Checkpointer requires ... thread_id。框架强制，防止你误以为在续聊其实没存上。

Q6：有 checkpointer 还必须每次传同一个 thread_id 吗？ 想续同一段记忆就传同一个；想开新对话就换。

Q7：模型能直接“看”到 checkpointer 存的快照吗？ 不能直接看。它通过 messages 间接看到（快照里的 messages 被铺回）。所以 54 课说“自定义键不进 prompt”依然成立。

Q8：Store 和 Checkpointer 会冲突吗？ 不会，两套独立机制，一个管会话进度、一个管业务档案，可同时挂（47 课就是同时挂的）。

七、一句话收口

📌 短期记忆 = State（载体）＋ Checkpointer（留住）＋ Thread ID（寻址）。
📌 内部机制：每次 invoke 先按 thread_id 取快照→合并输入→跑循环每步存盘→收工存回。
📌 “2→4 条消息”=历史续上的铁证；InMemorySaver 进程退出即失，换 SqliteSaver 才落盘长期。
📌 Checkpointer 管“对话到哪了”，Store 管“某用户资料”，两者粒度不同、互不冲突。
