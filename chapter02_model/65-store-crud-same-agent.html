第65讲 · 同一个 agent 内，store 的「增删改」

文件：65-store-crud-same-agent.py（已实跑，含 store 真身打印）｜ 对照：60/61 context、62/63 state

直接回答：store 增删改全部「运行时动态可控」，且跨线程共享

操作API同一 agent 内
增store.put(ns, key, {...})✅ 随时写新键
改同 ns+key 再 put✅ 覆盖整条（局部改要 get→改→put）
查store.get(ns, key) / store.search(ns)✅
删store.delete(ns, key)✅ 随时删键

和 state/context 的根本区别：state/context 的 schema 在编译期冻结，属性增删运行时做不到；store 没有 schema，是一个纯键值档案柜，运行时想加哪条、删哪条都行，而且不按 thread 隔离、跨会话共享（这才是"长期记忆"）。

先看怎么把 store 挂进 agent

from langgraph.store.memory import InMemoryStore

store = InMemoryStore()          # 独立对象，同一进程里跨线程共享

agent = create_agent(
    model=llm, tools=[upsert_pref, read_pref, list_prefs, del_pref],
    system_prompt="根据用户要求调用对应工具...",
    state_schema=MessagesState,
    store=store,                 # ← store 从 create_agent 的 store= 参数挂进去
    checkpointer=InMemorySaver(),
)

工具里可以用 runtime.store 访问（47 课），也可以直接用模块里的 store 对象——因为是同一个引用。本 demo 用后者，代码更直观。

① 增：store.put(ns, key, value) —— 随时写新记录

ns = ("users", "u1")
store.put(ns, "prefs", {"hobby": "天文", "lang": "中文"})

并且写在一个线程，另一个线程立刻能读到（store 不按 thread 隔离）：

实跑输出（store 真身，不靠模型复述）： [store 真身] u1/prefs = {'hobby': '天文', 'lang': '中文'} t_read (不同线程!) 调 read_pref → 读到的也是 {'hobby': '天文', 'lang': '中文'} ← 另一个线程读到了：store 跨线程共享（state 做不到）

对比：state 是按 thread_id 隔离的——t1 写的 state，t2 读不到。store 恰恰相反，天生用来"跨会话记住"。

② 改：同 ns+key 再 put = 覆盖整条（⚠️ 没有局部更新）

# 错误示范：直接 put 一个只有 lang 的 dict → 整条被替换，hobby 丢
store.put(("users","u1"), "prefs", {"lang": "英文"})
实跑输出： [store 真身] u1/prefs = {'lang': '英文'} ← hobby 没了（整条覆盖）

正确做法是先 get 出来 → 改 → 整体 put 回去（这就是 demo 里 upsert_pref 干的事）：

item = store.get(ns, "prefs")
val = dict(item.value) if item else {}   # 先取旧值
val["hobby"] = "天文"                     # 改
store.put(ns, "prefs", val)              # 整体写回
恢复后 [store 真身] u1/prefs = {'lang': '中文', 'hobby': '天文'} ← 两字段都在
坑（48/49 课也讲过）：put 是整条覆盖，不是字典 merge。想"只改一个字段"，必须自己 get→改→put，否则其他字段被抹掉。

③ 查：get 单条 / search 批量

store.get(("users","u1"), "prefs")    # 单条，返回 Item 或 None → .value
store.search(("users",))              # 前缀批量，返回 list[Item]
实跑输出： [store 真身] search(('users',)) = [(('users','u1'), 'prefs', {'lang':'中文', 'hobby':'天文'})]

search 的 namespace 是前缀查询：给 ("users",) 会列出 users 下所有用户的记录；给 ("users","u1") 只列 u1 的。

④ 删：store.delete(ns, key) —— 删后再查为 None

store.delete(("users","u1"), "prefs")
实跑输出： [store 真身] get u1/prefs = None ← None 表示已删

删的是单条（ns + key 定位）。删整个 namespace 需要遍历 search 出来的每条去 delete（store 没有"删目录"API）。

⑤ 三种上下文/记忆的增删改总对照

维度contextstatestore
形态单个对象（dataclass）TypedDict（字段=通道）键值档案柜（ns+key→dict）
增属性/记录❌ schema 冻结❌ 未声明键被忽略✅ 随时 put 新 key
改值✅ 但需重传实例✅ Command 写回，记住✅ put 覆盖整条
删属性/记录❌ 只能不传❌ 只能覆盖值✅ delete 真删
跨 invoke 记住❌ 不记✅ 同 thread 记✅ 跨 thread/跨会话
隔离性无状态按 thread_id 隔离全局共享
典型用途本次调用的环境配置单次会话的白板/进度长期用户偏好/知识

小结

  • 同一个 agent 内，store 的增/改/查/删全部运行时动态可控——这是它和 state/context 最大的不同（后两者属性增删被 schema 冻结）。
  • store 跨线程共享：一个 thread 写，另一个 thread 立刻读到；state 是 thread 隔离的，读不到。这就是"长期记忆 vs 短期记忆"的分水岭。
  • 改要小心：put 是整条覆盖，不是 merge；要局部改必须 get → 改 → put。
  • 记住三条键规则（48/49 课）：namespace 是元组（多级路径）、key 是字符串、value 必须是dict。
