50 · 两个类定义详解：@dataclass AppContext 和 MyState(MessagesState)

这是 47 课 demo 里最"Python 语法密集"的两段。核心是回答两个问题： ① @dataclass 是什么魔法？② 为什么 state 用继承、context 用装饰器？

① @dataclass —— "只写字段，构造器白送"

@dataclass 是 Python 标准库的装饰器（不是 LangChain 的东西）。它的魔法就一件事： 扫一遍类里写的 字段名: 类型 声明，自动帮你生成 __init__、__repr__、__eq__。

没有它你得手写这些样板代码：

# 不用 dataclass 的原始写法（又长又容易错） class AppContext: def __init__(self, user_id, env, db_host): self.user_id = user_id self.env = env self.db_host = db_host def __repr__(self): ... # 还得手写打印格式

用了它，只写三行字段声明，构造器/打印/相等比较全自动（实验证实）：

c = AppContext(user_id='u-1', env='test') # __init__ 白送 ✓ print(c) # AppContext(user_id='u-1', env='test') ← __repr__ 白送 ✓

user_id: str 这种写法叫类型注解：声明"这个字段叫这名、应该是这种类型"。 普通类里注解只是注释；但 dataclass 正是靠读这些注解来生成构造器的——所以注解在这里不是装饰，是原料。

为什么 context_schema 必须是个类？

LangGraph 要求 context_schema 传一个类型：它拿这个类型做两件事—— ① 校验你 invoke 时传的 context=AppContext(...) 是不是这个形状； ② 把实例通过 runtime.context 递给工具，工具里才能点属性访问 ctx.env。 用 dataclass 定义它是最省事的姿势：三行字段换来完整的构造+校验+打印。

② class MyState(MessagesState) —— 继承"自带 messages 的表"

MessagesState 的真身不是普通类，是 TypedDict（实验：type(MessagesState) → _TypedDictMeta）。 TypedDict 是"给 dict 标注键和类型的表结构"——它描述一张 dict 长什么样，不是定义对象。

它自带一个键（实验读出）：

messages: Annotated[list[AnyMessage], add_messages]

这个注解里藏着 LangGraph 的核心机制：add_messages 是 reducer（合并策略）—— 每个节点返回新 messages 时，不是覆盖整个列表，而是追加合并。这就是聊天历史能越滚越长的原因。

而 class MyState(MessagesState) 的继承，含义就是"在这张表上加我的键"（实验证实）：

MyState 继承后全部键 = {'messages': ..., 'user_name': str} ↑ 继承来的 ↑ 我加的

实例就是 dict（实验：isinstance(..., dict) → True）——所以工具里 runtime.state.get('user_name')、state['messages'] 全是字典访问。

③ 为什么一个用装饰器、一个用继承？（对照表）

AppContext（@dataclass）MyState(MessagesState)
真身普通类 + 自动生成方法TypedDict 子类（描述 dict 的表）
实例长什么样对象，点属性：ctx.env就是 dict，键访问：state['user_name']
可变性静态：invoke 时传入，运行中不变（工牌）动态：节点不断往里写（白板），reducer 定合并规则
为什么选这种写法要的是"一组带类型的参数包"，dataclass 三行搞定构造要的是"在已有表上加键、继承合并策略"，TypedDict 继承天然干这个
类比印刷好的工牌（进场前定稿）车间白板（边干边写，add_messages 决定"追加不覆盖"）
💡 一句话：dataclass 管"打包一组静态参数"（写一次用一次）； TypedDict 继承管"声明一张会演变的表"（继承旧键+合并规则，再加新键）。 两套语法服务两种数据，所以姿势不同。

④ 呼应 43 课的 dict 坑

43 课踩过：wrap_tool_call 的 request.tool_call 是 dict（键访问）、 wrap_model_call 的 request 是对象（点属性）。现在你知道根源了： LangGraph 里"state 系"数据全是 TypedDict（dict），"context/config 系"数据是普通类（对象）。 拿到一个东西先分清它属于哪系，就不会再混。
