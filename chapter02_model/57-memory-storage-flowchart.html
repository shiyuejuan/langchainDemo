57 · 短期记忆 · 数据存储位置流程图

重点回答：“数据到底存在哪？”——State、Checkpointer、Thread ID 三个角色，物理上数据落点不同。

RAM 进程内存（程序关就丢）
磁盘文件（程序关还在）
钥匙（不是仓库）
① 你敲代码
agent.invoke({"messages":[...]}, config={"thread_id":"t1"})
▼
② State 字典在 RAM 里生成
这是一次运行的内存中的字典：messages 列表 + 你加的字段（如 user_name）。
物理位置：进程内存（RAM），运行结束本就该清空——但有了下面第④步才留得住。
▼
③ agent 跑循环（model→tool→model…）
每跑完一个“步”，就把当前 State 交给 Checkpointer 处理。
▼
④ Checkpointer（cp 对象）把 State 拍快照
cp 用 thread_id="t1" 当钥匙，把快照存进“存储后端”。
Thread ID 只是钥匙/编号，本身不存数据。
▼
⑤ 存储后端（决定数据物理落点）
InMemorySaver（55/56 课用的）→ 快照存进 RAM 内存
→ 程序一退出，内存清空，全忘。这就是“短期”。
SqliteSaver.from_conn_string("mem.db")（换一行代码即可）→ 快照存进 磁盘 .db 文件
→ 程序退出仍在，下次还能读。这就变成“长期”。
▼
⑥ 下次 invoke（同一个 thread_id="t1"）
cp 用同一把钥匙 "t1" 去存储后端取出快照 → 铺回 State。
（56 课实跑：返回 messages 从 2 条变成 4 条，旧 2 条就是这时取回的）
▼
⑦ 模型读取 State 里的 messages 续聊
注意：模型只看到 messages，自定义字段（如 user_name）不会自动进 prompt（54 课）。

两张图对照：数据物理落点

State → 活在 RAM（单次运行的内存字典） Checkpointer → 决定把 State 的快照存去哪：RAM（InMemorySaver）或 磁盘（SqliteSaver） Thread ID → 只是 Checkpointer 寻址用的钥匙字符串，不是仓库本身 记忆“短/长”之分，只取决于 Checkpointer 用哪种后端： InMemorySaver = 内存 = 短期（进程退出即失） SqliteSaver = 磁盘 = 长期（退出仍在） 两者机制完全一样，只换“抽屉材质”。
📌 一句话：State 这张纸写在 RAM；Checkpointer 决定把纸复印一份存内存还是存磁盘；Thread ID 是标着“t1”的抽屉钥匙。 没有 Checkpointer → 纸用完就扔（金鱼脑）；有 Checkpointer 但用 InMemorySaver → 纸存内存，程序关了就没。
