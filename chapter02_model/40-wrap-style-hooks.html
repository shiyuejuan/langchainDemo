5.4 Wrap-style hooks：包住调用的函数式写法

钩子型（5.3 的 @before_model / @after_model）wrap 型（本节 @wrap_model_call / @wrap_tool_call）
函数签名(state, runtime)(request, handler)
角色车站：发车前后看一眼 / 动 state包住整趟列车：改请求、改结果、短路
返回值None / dict(状态更新) / Command必须 return handler(request) 或其加工版
装饰器参数name / state_schema / tools / can_jump_toname / state_schema / tools（没有 can_jump_to——它不在图路由里）
结构顺序节点洋葱嵌套（第 35 课实跑过）

wrap 型函数的三种玩法

① 放行：return handler(request) —— 纯日志/监控（demo ① 的 4 行日志中间件）。
② 改写后放行：return handler(request.override(...)) —— 注入 system_message、裁剪 messages、换 model（ModelFallbackMiddleware 就是这么干的）。
③ 短路：不调 handler，直接 return 自己构造的结果 —— 工具模拟器（LLMToolEmulator）就是这种。

实跑亮点：事前注入 vs 事后质检

39 课让回答带"完毕"用的是事后方案：after_model 质检 → 不合格附提示 → jump_to model 重答（多花一次模型调用）。
本节用 wrap 型事前方案：request.override(system_message=原要求+"\n结尾带'完毕'") —— 请求发出前就把规矩立好，一次到位，零跳转、零重试。实跑最终回答结尾确实带上了"完毕"。
怎么选：能事前立规矩就事前（省 token）；事后质检适合兜底"模型不听话"的场景。

实跑细节备忘

① handler 返回的是 ModelResponse 类型（模型响应的封装，不是裸 AIMessage）。
② name 参数可自定义中间件名（默认取函数名）；state_schema / tools 与钩子型一致。
③ 改 system_message 时先接住旧的再拼接（request.system_message.content），别把 agent 原有系统提示冲掉。
