58 · 短期记忆：到底存了什么内容？

57 课讲了“数据存在哪”（RAM / 磁盘）。这一课讲“快照里具体装了哪些东西”——直接打印真实结构，不讲故事。

一、真实打印：抽屉里的快照长这样

跑一遍带自定义字段 user_name 的 agent，再用 cp.get_tuple(CFG) 打开抽屉，打印出来的内容：

=== 抽屉里 channel_values（被存下来的“内容”）=== 键名: ['messages', 'user_name'] messages 条数: 2 user_name = 小明 === 快照自己的元信息 checkpoint 字典键 === ['v', 'ts', 'id', 'channel_versions', 'versions_seen', 'updated_channels', 'channel_values'] ts(时间戳) = 2026-10-31T02:50:30... id(快照版本号) = 1f1d4d5d-... === 执行进度 pending_writes === []

二、拆开看：快照 = 两大部分

第 ① 部分：你的 State 全部字段（channel_values）

这是被存下来的“内容”本体。它不是一个单独变量，而是你 state 里的所有键：

  • messages：整段对话（每条用户/AI/工具消息）——这是“记忆”的主体；
  • user_name：你自定义的字段，也原样存进去了（上面打印里 user_name = 小明 就是证据）。

→ 换句话说：state 里写了什么，快照就存什么，一个不漏。你加了 user_name 它就存 user_name；加了别的字段也照存。

第 ② 部分：图的执行进度 + 元信息（不是你写的内容）

字段是什么
ts时间戳（这版快照什么时候拍的）
id快照版本号（同一 thread_id 每更新一次换一个 id）
channel_versions每个 channel（如 messages）的版本号，用来判断“哪份更新”
pending_writes“任务现场”——当前停在哪个节点、还有哪些写入没落地。让图可以中途断点续跑

这部分是 LangGraph 自己用的“运行档案”，不是你的业务数据，但正因为有它，记忆才能精确地从中断处续上。

三、对照：什么被存了，什么没被存

会被存进快照不会存（在别处）
✅ 整段 messages 对话❌ 你的 Python 代码 / agent 定义
✅ state 里所有自定义字段（user_name 等）❌ 工具的定义（@tool 函数）
✅ 执行进度（pending_writes）❌ 模型本身（权重在远端服务器）
✅ 时间戳 / 版本号等元信息❌ API Key（在环境变量 / .env 里）

一句话：快照只存“这次对话进行到哪了”这件事本身（对话内容 + 进度），不存“怎么跑起来”的程序和密钥。 程序下次启动重新加载，再用 thread_id 把快照取回来续上就行。

四、呼应 54 课（为什么存了 user_name 模型仍答小明）

54 课你问：第 2 轮把 user_name 改成“明明”，回答却还是“小明”。真相在这里揭晓—— user_name="明明" 确实被存进了快照的 channel_values（和前面打印的“小明”同理）。 但模型只读取 messages 来生成回答，不会自动去翻 channel_values 里的 user_name。 所以“存了”和“模型用没用”是两回事：存了（在抽屉里），但没人把它写进 messages 喂给模型。

📌 快照内容 = 你的 state 全部字段（messages + 自定义字段）+ 图执行进度 + 元信息。
📌 你 state 里写什么，它就存什么；你加 user_name 它就存 user_name。
📌 存的是“对话进行到哪了”，不是代码、不是模型、不是密钥。
📌 user_name 被存了但模型不自动读它 → 这正是 54 课那个现象的根。
