第 09 章 · 66 SqliteSaver：把对话保存到数据库

这节课把 59 课计数器的 InMemorySaver 换成 SqliteSaver，专门验证一句话： 对话和状态真的落到磁盘文件里，进程退出后再打开，记忆还在。 这正是 57 课我们画的 RAM（蓝）/磁盘（绿）流程图的"绿色那一步"。

为什么需要它（先说问题）
前面所有 demo 用的 InMemorySaver 把 checkpoint 存在 内存（RAM） 里。 进程一退出（关终端、关电脑、重启服务），内存清零，记忆全没。 SqliteSaver 把同样的东西写进一个 .sqlite 文件，进程重启后文件还在，记忆就还在。

1. 真实 API（查源码确认，不是猜）

# 安装（1.x 拆成了独立可选包，默认不装）：
# uv pip install langgraph-checkpoint-sqlite

from langgraph.checkpoint.sqlite import SqliteSaver

# from_conn_string 是【上下文管理器】（@contextmanager）
with SqliteSaver.from_conn_string("checkpoints.sqlite") as saver:
    agent = create_agent(model=llm, tools=[...], checkpointer=saver)
    # with 块结束自动关连接，但 .sqlite 文件留在磁盘

# 也支持内存模式（和 InMemorySaver 等价，进程退出即失）：
# with SqliteSaver.from_conn_string(":memory:") as saver:

源码里的关键签名（已读）：

@classmethod
@contextmanager
def from_conn_string(cls, conn_string: str) -> Iterator[SqliteSaver]:
    with closing(sqlite3.connect(conn_string, check_same_thread=False)) as conn:
        yield cls(conn)
注意两点：
  • from_conn_string 返回的是 上下文管理器，必须用 with 包起来用； 文件里直接写 saver = SqliteSaver.from_conn_string(...) 然后不用 with 也行，但要自己管连接关闭。
  • check_same_thread=False 是框架内置的，解决 SQLite 多线程报错，不用你操心。

2. 换后端只改一行

短期记忆三件套（State + Checkpointer + Thread ID）里，只有 Checkpointer 换了，其余完全不变：

对比内存版（59 课）磁盘版（本课）
CheckpointerInMemorySaver()SqliteSaver.from_conn_string("x.sqlite")
state / 工具 / prompt完全一样（MyState + bump 工具）
thread_id 寻址完全一样（{"configurable":{"thread_id":"t1"}}）
进程退出后记忆全丢文件留存，记忆还在

结论：SqliteSaver 和 InMemorySaver 都是 BaseCheckpointSaver 子类，接口完全一致， 所以"短期记忆变长期（落盘）"在生产里往往就是改这一行。

3. 实跑证据：进程重启后记忆还在

阶段一第一次运行，连问 3 次，counter 累加，数据写进 .sqlite 文件。 此时即便进程没结束，文件已经 126976 bytes 了。
阶段二模拟"进程重启"：阶段一的 with 已关闭（连接断开）， 我们重新打开同一个文件，并造一个全新的 saver2 + 全新 agent2——完全不依赖阶段一的内存。 什么 invoke 都没做，直接读，counter 立刻 = 3（从磁盘加载）。再问第 4 次 → counter = 4（接着 3）。
对照全新 InMemorySaver 读同一线程 → None，证明内存里确实啥都没有。
==================== 阶段一：第一次运行，对话写到 .sqlite 文件 ==================== [阶段一结束后（在 with 块内读）] counter=3 | messages 条数=12 此时磁盘上数据库文件：checkpoints_demo.sqlite 大小=126976 bytes ==== 阶段二：模拟进程重启 —— 重新打开同一个 .sqlite 文件 ==== 数据库文件还在吗：True 大小=126976 bytes [重启后立即读（没做任何 invoke）] counter=3 | messages 条数=12 [重启后第 4 次 invoke 之后] counter=4 | messages 条数=16 ==== 对照实验：全新 InMemorySaver 读同一个 thread_id ==== [全新 InMemorySaver] get_tuple → None（没有任何 checkpoint） ==== 阶段三：直接用 sqlite3 打开文件，看数据库里的表 ==== 数据库里的表： ['checkpoints', 'writes'] checkpoints 表（按线程统计记录数）： [('t1', 20)]

怎么读这段输出：

  • counter=3 → 4：重启后第 4 次 invoke 是在"3"的基础上 +1，而不是从 0 重来。 这证明 counter 这个 自定义 state 字段也跟着 checkpoint 落盘了，不只是 messages。
  • 全新 InMemorySaver → None：对照组，说明"能读到 3"不是因为缓存，而是文件里真有数据。
  • checkpoints / writes 两张表：框架把"每个线程的快照"存在 checkpoints， 把"工具的中间写入"存在 writes。t1 有 20 条记录（4 轮对话 × 5 个写入点）。

4. 这到底是不是"长期记忆"？

维度SqliteSaver（本课）store（47/65 课）
存什么每个 thread 的对话快照（state 全量）任意键值（用户偏好等）
隔离单位按 thread_id 隔离按 namespace 组织，跨线程共享
进程重启文件留存，记得内存版不留存；换持久化后端才留存
典型用途单段对话的"短期记忆"（不丢）跨会话的"长期记忆"（用户档案）

所以：SqliteSaver 解决的是"短期记忆别因为重启而丢"（同线程历史不灭）； store 解决的是"跨所有会话长期记住某人"。两者职责不同，常配合使用。

5. 几个实战提醒

  • 文件位置：from_conn_string("checkpoints.sqlite") 是相对路径，文件生成在"运行脚本的目录"。 生产里建议写绝对路径，并把它加入 .gitignore（别把用户对话提交进仓库）。
  • 并发：SQLite 是单文件库，多个进程同时写同一文件会锁。生产高并发建议换 langgraph-checkpoint-postgres（Postgres 后端，API 一样只换一行）。
  • 清理：想从头开始，删掉 .sqlite 文件即可（本课 demo 开头就 os.remove(DB) 保证每次干净）。
  • 不是加密：.sqlite 是明文数据库，敏感对话注意权限或加密。
一句话总结
短期记忆三件套（State + Checkpointer + Thread ID）里，把 InMemorySaver 换成 SqliteSaver.from_conn_string("xxx.sqlite")，对话和自定义字段就落盘了； 进程重启后重新打开同一文件，历史还在——生产里"短期记忆变长期（不丢）"往往就是这一行的事。 要"跨会话记住某个人"，那是 store 的活儿，不是 checkpointer 的。
