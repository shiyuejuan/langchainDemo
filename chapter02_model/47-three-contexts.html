47 · 三种上下文一锅端：state / store / context

对应课程 1.2.2 上下文类型及相关的 API。上一讲说了"上下文工程是模型只知道你给它看的东西"， 这一讲回答的是：那些"给它看的东西"分别放在哪、活多久、能不能改？ LangGraph 给了三种"容器"，按可变性 × 生命周期两个维度划分：

一、三种上下文总表（对应课程表格的实跑版）

上下文类型类比可变性生命周期访问方式（实跑确认）
动态运行时上下文
state		 🧰 车间白板：运行中谁都能往上写，下班（运行结束）就擦 动态（可变）单次运行（配 checkpointer 可跨 invoke 续） 工具里 runtime.state
组装时 state_schema=MyState
动态跨会话上下文
store		 🗄️ 档案柜：今天来查、明天来还能查到，跨对话共享 动态（可变）跨对话（持久） 工具里 runtime.store.get(...)
组装时 store=InMemoryStore()
静态运行时上下文
context		 🎫 进场工牌：进场（invoke）时发，上面写死你是谁、连哪个库，运行中不许改 静态（只读）单次运行 工具里 runtime.context
组装时 context_schema=AppContext
调用时 agent.invoke(输入, context=AppContext(...))
💡 一句话记忆法：白板（state）随便写但下班就擦；档案柜（store）存得久还跨对话；工牌（context）只管这一次进场、进完场不许改。

二、demo 实跑：一个工具同时摸三种上下文

关键角色是工具参数 runtime: ToolRuntime——它身上正好挂着 state / store / context 三个字段，工具内部全都能读到：

【工具内部实况】三种上下文，工具里全都摸得到：
① state   类型=dict
   键有哪些：['messages', 'user_name']
   消息条数=2，自定义键 user_name='小明'
② store   类型=InMemoryStore
   查档案柜 (users, xiaoming)/preferences → {'language': '中文', 'style': '简短', 'hobby': '天文'}
③ context 类型=AppContext
   工牌内容：user_id=u-1001, env=test, db_host=db-internal:5432

① state：车间白板

组装时用 state_schema=MyState 扩展默认状态，加自定义键 user_name； invoke 时把它随输入传进去 → 工具里 runtime.state["user_name"] 读到 '小明'。

第 2 次 invoke 同线程再问，消息条数 2→6（checkpointer 续上历史，45 课机制）， 回答"你是小明"——白板被带着走。

② store：档案柜

会话开始前先放一条：store.put(("users","xiaoming"), "preferences", {...})。 工具里凭命名空间+key 取：runtime.store.get(("users","xiaoming"), "preferences")。

它不依赖任何 thread_id——换线程、换会话都还在，所以是"跨对话"。存用户偏好、画像、长期知识用它。

③ context：进场工牌

组装时声明 context_schema=AppContext（dataclass），调用时传实例。

工具里 runtime.context.env 直接点属性——像 43 课说的，context 是对象不是 dict， 和 state 的字典访问方式不同。

三、实踩的坑（两个都是真坑）

坑① context 不是塞在 config 里！

我第一版写的是 config={..., "context": AppContext(...)} → 工具里读到 runtime.context = None，直接 AttributeError: 'NoneType' object has no attribute 'user_id'。

正确姿势：context 是 invoke 的顶层关键字参数：

agent.invoke(输入, config={"configurable": {"thread_id": "t1"}},
             context=AppContext(...))   ← 顶层 kwargs，不进 config

最小实验验证：塞 config 里 → None；顶层 kwargs → Ctx(env='test-A') 正常到达。

坑② 跑通后有一串 Pydantic 序列化警告

PydanticSerializationUnexpectedValue ... field_name='context'——不影响结果，属于 1.x 序列化器对自定义 dataclass 的提示性警告，demo 阶段可忽略；生产上可考虑换成 Pydantic 模型定义 context_schema。

四、和已学内容的对接（知识网收口）

新概念接住它的旧知识
state（单次运行白板）45 课 checkpointer：给白板"拍照存档"，下次 invoke 自动铺回来
store（跨会话档案柜）45 课表格里"③ 换 thread_id 不串台"的另一半：线程隔离靠 checkpointer，跨线程共享靠 store
context（静态工牌）46 课上下文工程"选 Select"策略的一种落地：连接串、用户 ID 这类"不该让 LLM 看到的运行参数"走 context，不占提示词
ToolRuntime 注入和中间件的 runtime 参数同一血统（36-44 钩子家族）：框架在调用瞬间把"现场"塞给你

五、三句话记住

  1. state 管这一次：运行中可变，checkpointer 让它能续；工具里 runtime.state。
  2. store 管一辈子：跨对话持久，命名空间+key 存取；工具里 runtime.store。
  3. context 管进场：invoke 时顶层 context= 传入、只读；工具里 runtime.context。 千万别塞进 config！
