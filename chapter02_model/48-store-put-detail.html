48 · InMemoryStore 三行代码逐行详解

对应 47 课「store = 档案柜」那段。下面把你贴的三行拆开讲，再补上它没写出来、但生产必须知道的 四个隐藏行为（其中第 1 条是我实跑踩出来的真坑）。

# ① 建一个内存档案柜 store = InMemoryStore() # ② 会话开始前，先往档案柜里放一条用户偏好（namespace, key, value） store.put(("users", "xiaoming"), "preferences", {"language": "中文", "style": "简短", "hobby": "天文"})

① store = InMemoryStore() —— 建柜子

是什么：一个进程内的键值存储（key-value store）。数据存在 Python 进程的内存里。

“InMemory” 两个后果要记死：

  • ✅ 读写极快，不需要装数据库；
  • ❌ 程序一退出，数据全没（断电即失）。它只是“这次运行的档案柜”，不是真数据库。

生产替代：要真持久化，换 SqliteStore（落本地文件）或 LangGraph Platform 的托管 store。 接口完全一样（都是 put / get / search / delete），只改“柜子从哪来”。

它传给 create_agent(store=store)，框架在调用工具时把柜子通过 runtime.store 递给工具——这就是 47 课工具里 runtime.store.get(...) 摸到的那个柜子。

② store.put(namespace, key, value) —— 放东西

三个参数，对应“柜子里的三层定位”：

参数你的代码里含义（类比）实跑约束
namespace
tuple		 ("users", "xiaoming") 📁 文件夹路径（多级）。元组长度自由，用层级分租户/分用户/分类型。 第一级常放实体类型 "users"，第二级放具体 ID "xiaoming"。 必须是元组；search 时传前缀元组即可按层级批量找（见下）。
key
str		 "preferences" 🏷️ 文件夹里的文件名。同一 namespace 下靠 key 区分多条记录（如 preferences / orders / profile）。 字符串。
value
dict		 {"language":"中文", ...} 📄 文件内容本体——真正你想持久的业务数据。 必须 dict 见下方坑①。

🪤 坑①：value 必须是 dict，不能是 list / str / int！

我第一版探头里想存订单列表 [101,102]（非 dict），直接炸：

# 错误示范 store.put(('users','xiaoming'), 'orders', [101, 102]) # → TypeError: cannot convert dictionary update sequence element #0 to a sequence

InMemoryStore 内部会把 value 转成 dict(op.value)，所以只能是映射（dict）。 想存多个值，包一层字典即可：{'list': [101,102]}。这个约束不像“报错信息”那样直观，初学者极易中招。

③ {"language":"中文","style":"简短","hobby":"天文"} —— 你放的内容

就是一份普通的 Python 字典，存的是“小明的偏好”。可以是任意嵌套 dict / list，只要最外层是 dict。 47 课工具里这么取：

item = runtime.store.get(("users", "xiaoming"), "preferences") # item 是 Item 对象，真实数据在 .value print(item.value) # {'language':'中文','style':'简短','hobby':'天文'}

记住 get 返回的不是裸 value，而是 Item 对象——它身上还有 .key、.namespace、.created_at。 直接拿 item 当字典用会错，必须 item.value。

四、它没写出来、但你必须知道的行为（实跑验证）

行为 1：search 按 namespace 前缀批量查

不必精确知道 key，传前缀元组就能拉出整片：

for it in store.search(("users",)): # 所有用户 print(it.namespace, it.key, '->', it.value) # ('users','xiaoming') preferences -> {...} # ('users','xiaoming') orders -> {'list':[...]} # ('users','xiaohong') preferences -> {...} store.search(("users","xiaoming")) # 只查 xiaoming 名下两条

行为 2：同 namespace + key 再 put = 覆盖，不是追加

store.put(('users','xiaoming'), 'preferences', {'language':'中文','hobby':'天文','updated':True}) print(store.get(('users','xiaoming'),'preferences').value) # {'language':'中文','hobby':'天文','updated':True} ← 旧的 'style' 没了，整条被覆盖

所以要“改某个字段”，得先 get 出旧值、改完再 put 整条；没有“只补一个键”的原生 API。

行为 3：delete(namespace, key) 删除单条

store.delete(('users','xiaoming'), 'orders') # 删后 search(xiaoming) 只剩 ['preferences']

行为 4：跨线程/跨会话天然共享（它存在，checkpointer 不在）

store 是挂在 agent 上的独立对象，不属于任何 thread_id。所以：换 thread_id（45 课的“隔离”实验）它照样在； 不同用户的对话也能读到同一份 namespace 数据。这正是它和 checkpointer（按线程隔离）的本质区别—— store 用来存“该跨对话保留的”长期记忆（用户画像、偏好、知识），checkpointer 用来存“单次会话的聊天历史”。

五、记忆锚点

store 三件套 InMemoryStore()（建柜，进程内易失）→ put(tuple_ns, str_key, dict_value)（放，value 必 dict）→ get/ search/ delete（取/按前缀批量查/删）。

定位公式 namespace 像“文件夹路径（元组可多级）”，key 像“文件名”，value 像“文件内容（必 dict）”。

和 state/checkpointer 的分工 state=单次会话白板；checkpointer=单次会话历史（按线程隔离）；store=跨会话长期档案（不隔离）。
