第62讲 · state 的增删改（对照 context）

文件：62-state-crud-demo.py（已实跑验证）｜ 对照：60/61 的 context 增删改

先给总纲：state 和 context 在"增删改"上的本质不同

源码已证实（之前查过 StateGraph.__init__）：

  • state是 TypedDict（字典形态），编译时被 _add_schema 拆成一条条通道(channel)。每个字段 = 一条通道。会被 checkpointer 记住（进 channel_values）。
  • context是单个对象（dataclass/class），编译时不拆通道，只当类型标注。不进 checkpoint，不被记住。

所以一句话：state = 字典 + 通道 + 被记住；context = 对象 + 点属性 + 不记住。这决定了两者"增删改"的玩法完全不同。

① 设计期增删字段（改类定义 = 加/删通道）

state 的字段在 create_agent 那一刻由类定义冻结（和 context 的 schema 冻结同理）：

# 加一个字段 = 编译后多一条通道
class S(MessagesState):
    user_name: str = ""     # → 通道 user_name
    counter: int = 0        # → 通道 counter
    # 想再加 → 写一行 vip: bool = False；想删 → 删那一行
# 改完类定义必须「重建 agent」，旧 checkpoint 里被删通道的值不再被读取

这里和 context 一样："字段的增删"属于设计期，运行时改不了类定义。但 state 多了一层"通道"概念——加字段=加通道，这是 context 没有的。

② 运行时【改值】—— state 的核心能力，而且会被记住

工具用 Command(update={通道名: 新值}) 把新值写回某条通道。关键：写回后，同一个 thread_id 下一次 invoke 还能读到——这是 context 做不到的（context 每次都得重传）。

@tool
def set_name(q: str, runtime: ToolRuntime) -> Command:
    """把用户名设置为“明明”。"""
    return Command(update={
        "messages": [ToolMessage(content="已将 user_name 设为 明明",
                                 tool_call_id=runtime.tool_call_id)],
        "user_name": "明明",
    })

# 同一个 thread_id="a" 调两次
r1 = agentA.invoke({"messages":[...]}, config={"configurable":{"thread_id":"a"}})
r2 = agentA.invoke({"messages":[...]}, config={"configurable":{"thread_id":"a"}})  # 这次没调工具
实跑输出： 第 1 次 invoke 后, state['user_name'] = '明明' 第 2 次 invoke 后, state['user_name'] = '明明' ← 仍是明明，证明 state 被 checkpoint 记住 （对比：context 第 2 次不传就变 None，见 60 课）

这是 state 和 context 最关键的差别：state 的值跨 invoke 自动续命；context 的值每次都得你手动重传。

③ 运行时【增】一个 schema 没声明的键 —— 直接被忽略

既然 state 是字典，能不能运行时随便塞一个新键？实测：不能。因为通道在编译时就定死了，未声明的键不会被当通道，写了也被丢弃。

@tool
def add_extra(q: str, runtime: ToolRuntime) -> Command:
    """尝试写入一个 state 里没声明的字段 extra_field。"""
    return Command(update={
        "messages": [ToolMessage(content="尝试写入 extra_field",
                                 tool_call_id=runtime.tool_call_id)],
        "extra_field": "hello",    # ← 未在 class S 里声明
    })
实跑输出： invoke 返回里有没有 extra_field 键: False checkpoint channel_values 的键: ['messages', '__pregel_tasks'] （extra_field 既不在返回值，也不进 checkpoint —— 写了等于白写）

注：上面 channel_values 没显示 user_name/counter，是因为这是独立的 b 线程、从未写过它们；写过之后自定义字段会出现在 channel_values（56/58 课已验证）。结论只针对"未声明键"：被忽略。

④ 运行时【删】—— 只能覆盖值，不能删通道

想"删掉"一个 state 字段？运行时做不到删通道，只能把值覆盖成空/默认。通道本身由 schema 决定，删通道只能回①的设计期。

@tool
def clear_name(q: str, runtime: ToolRuntime) -> Command:
    """把 user_name 覆盖为空字符串（安全做法）。"""
    return Command(update={
        "messages": [ToolMessage(content="已将 user_name 置空",
                                 tool_call_id=runtime.tool_call_id)],
        "user_name": "",    # 覆盖，不是删除
    })
实跑输出： 置空后 state['user_name'] = '' 通道里仍有 user_name 键吗: True ← 删的是"值"，通道定义还在（由 schema 决定）

如果你用 Python del state["user_name"] 想真删键——runtime.state 是只读快照，根本不能 del；改 state 唯一正道是 Command(update=...)。

⑤ 一张表看全：state vs context 的增删改

操作statecontext
设计期加字段类定义加一行 → 多一条通道，需重建 agentdataclass 加一行 → 多一个属性，需重建 agent
运行时改值✅ 支持 Command 写回，自动跨轮记住✅ 支持 重传新实例，不记住
运行时增未声明键❌ 忽略 不进通道/不进 checkpoint❌ 不进 schema 换实例即消失（61课）
运行时删字段❌ 不能删通道 只能覆盖值（或设计期删）⚠️ 别用 del 删已声明字段 会崩（61课）
本质字典形态，字段=通道，被 checkpointer 留住单个对象，点属性，原样透传，不记忆

⑥ 一个关联坑：state 改了值 ≠ 模型看见了

重要：你用 Command(update={"user_name":"明明"}) 把值写进了 state 通道，但模型只认 messages 列表（54 课核心结论）。自定义字段不会自动进 prompt。
  • 想要模型"知道" user_name：要么用工具把它读出来写进 messages，要么写进 system_prompt 模板。
  • state 的"增删改"解决的是数据持久/跨轮传递，不是"让模型自动感知"。别混淆。

小结

  • state 增删改的真相：字段增删在设计期（改类定义+重建）；运行时只能改值（Command 写回，自动记住），不能增未声明键（被忽略）、不能删通道（只能覆盖值）。
  • 和 context 对照：两者"设计期增删字段"一样要重建；但 state 的值被记住、context 的值不记住——这是选 state 还是 context 的分水岭。
  • 动态键值 + 跨会话长期记住 → 那是 store 的活儿（put/get/search/delete，47/48/49 课），state/context 都不擅长。
