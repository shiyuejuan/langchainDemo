1文件头 & 导入

# -*- coding: utf-8 -*- """47 · 三种上下文一锅端：state / store / context ...""" import os from dataclasses import dataclass from langchain.agents import create_agent from langchain.tools import tool, ToolRuntime from langchain_openai import ChatOpenAI from langgraph.checkpoint.memory import InMemorySaver from langgraph.store.memory import InMemoryStore from langgraph.graph import MessagesState

导入分四股：① 模型接入（ChatOpenAI，DeepSeek 走 OpenAI 兼容接口）； ② agent 工厂 create_agent；③ 工具相关 tool（装饰器）+ ToolRuntime（注入给工具的"现场包"）； ④ 三套存储：InMemorySaver（checkpointer）、InMemoryStore（store）、MessagesState（state 基类）。

2模型：用 ChatOpenAI 对接 DeepSeek

deepseek = ChatOpenAI( model="deepseek-chat", api_key=os.environ["DEEPSEEK_API_KEY"], base_url="https://api.deepseek.com/v1", temperature=0, )

DeepSeek 提供 OpenAI 兼容接口，所以直接用 ChatOpenAI 套一层、改 base_url 即可。 temperature=0 让回答尽量确定，做实验时输出稳定、好对比。

小坑：原文件用 os.environ["DEEPSEEK_API_KEY"]（中括号、缺了就崩）。 实测运行时要用 source .env 把 key 导进环境，否则 KeyError。 更稳的写法是 os.getenv("DEEPSEEK_API_KEY")（缺了返回 None 不崩）。

3③ 静态上下文：AppContext（工牌）

# ③ 静态运行时上下文：context_schema —— 启动时传入、运行中不变 # 类比：进场时发的"工牌"，上面写死了你是谁、连的哪个库 @dataclass class AppContext: """本次运行开始前就定死的元数据""" user_id: str env: str # prod / test db_host: str # 模拟"数据库连接"这类静态资源

这是 context：运行时定死、中途不变的"工牌"。用 @dataclass（50/50b 讲过）三行字段换来自动构造。 后面传给 create_agent(context_schema=AppContext)，调用时 context=AppContext(...)， 工具里用 runtime.context.user_id 点属性访问（卡片用点）。

4① 动态上下文：MyState(MessagesState)（白板）

# ① 动态运行时上下文：state —— 单次运行内会"演变"的可变数据 # 除默认 messages 外，加一个自定义键 user_name class MyState(MessagesState): user_name: str # 自定义键，随运行演变

这是 state：单次运行中可变的"白板"。MessagesState 是 TypedDict（50 讲过），自带 messages 键且用 add_messages reducer 追加。这里继承它再加一个 user_name 栏。 工具里用 runtime.state.get('user_name') 字典访问（便签纸用方括号）。

5② 跨会话上下文：InMemoryStore + put（档案柜）

store = InMemoryStore() # 会话开始前，先往档案柜里放一条用户偏好（namespace, key, value） store.put(("users", "xiaoming"), "preferences", {"language": "中文", "style": "简短", "hobby": "天文"})

这是 store：跨对话共享的"档案柜"。put(("users","xiaoming"), "preferences", dict)： namespace 是多级文件夹路径（49 讲过）、key 是文件名、value 必须是 dict（48 的坑①，传 list/str 会 TypeError）。 后面工具里 runtime.store.get(("users","xiaoming"), "preferences").value 取出 —— 注意 get 返回 Item 对象，真实数据在 .value。

6关键角色：my_info 工具（同时摸三种上下文）

@tool def my_info(question: str, runtime: ToolRuntime) -> str: """汇报我在工具里能看到的三种上下文。""" state = runtime.state # ① item = runtime.store.get(...) # ② ctx = runtime.context # ③

这一行是整份 demo 的灵魂：runtime: ToolRuntime

工具函数多写一个 runtime 形参（类型标 ToolRuntime），框架在调用工具瞬间自动把"现场"塞进来， 不用你手动传。这个 runtime 身上一次挂着三个字段：state / store / context， 所以一个工具就能把三种上下文全读到（实跑打印见 47 课 HTML）。

这也和 36-44 课的中间件 runtime 同一血统：框架在关键时刻把"现场包"交给你。

question: str 是给 LLM 看的参数（工具签名的一部分）；runtime 不会暴露给模型，纯给代码用。

7组装 agent：四套东西一次挂齐

agent = create_agent( model=deepseek, tools=[my_info], system_prompt="你是助手。需要环境信息时调用 my_info 工具……", state_schema=MyState, # ① 自定义 state context_schema=AppContext, # ③ 静态 context store=store, # ② 跨会话 store checkpointer=InMemorySaver(), # 让 state 跨 invoke 续上 )

create_agent 的参数（inspect 实查过）里这四个正是三上下文的"挂点"： state_schema / context_schema / store；外加 checkpointer 让 state 能按 thread_id 跨 invoke 续上（45 课机制）。 system_prompt（不是 prompt，46 课踩过）告诉 LLM 什么时候该调工具。

8调用：两行 invoke，藏着大坑

CFG = {"configurable": {"thread_id": "t1"}} CTX = AppContext(user_id="u-1001", env="test", db_host="db-internal:5432") r1 = agent.invoke( {"messages": [{"role":"user","content":"我是谁？我的偏好和环境是什么？"}], "user_name": "小明"}, # ① state 键随输入进来 config=CFG, context=CTX, # ③ context 是【顶层关键字参数】 )

🪤 大坑：context 不进 config！

第一版写成 config={..., "context": AppContext(...)} → 工具里读到 runtime.context=None， 直接 AttributeError。正确姿势是 agent.invoke(input, config=CFG, context=CTX)—— context 是 invoke 的顶层 kwargs，不是 config 里的一项（最小实验验证过）。

第 2 次 invoke：验证白板被带着走

同 thread_id="t1" 再问，state 的历史被 checkpointer 续上——消息条数 2 → 6。 且把 user_name 改成 "明明" 再次输入，证明 state 是"运行中的白板"，可以演变。 而 store（档案柜）换线程/换会话都还在，context（工牌）每次 invoke 重新发。
