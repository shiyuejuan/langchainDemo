50b · @dataclass 和 TypedDict 人话版

上一篇术语太多，这里一个术语一个比喻，把两行代码讲成"生活小事"。

🎯 先记总纲：这两段代码，其实只干了两种日常动作—— ① 印一张工牌模板（@dataclass）；② 在标准表格上加一栏（继承 MessagesState）。

一、@dataclass = "填空题，让机器帮你写阅卷规则"

你只写一句话："我这张工牌上有 user_id、env、db_host 三个格。"

按老办法，你还得再写一大段"怎么把这三个格装进卡里、怎么打印"的代码——又臭又长。

@dataclass 做的事就一句："那一大段'装填+打印'的代码，Python 替你自动生成，别写了。"

比喻：你只写"试卷有 3 道填空题"，监考老师（@dataclass）自动把答题卡怎么收、怎么打印都备好了。你只管AppContext(...) 填答案。

所以：user_id: str 不是废话，是"原料"——@dataclass 正是靠这三行原料造出整套规则。

二、MessagesState = "一张早就印好的表"

它不是一个能装的盒子，是"一张规定好长啥样的表"。它自己就带一个格子，叫 messages。

这个格子有点特殊：你往里加新消息，不是把整张表重写，而是贴到后面追加（专业词叫 reducer，但你记住"追加不覆盖"就行）。

比喻：messages 是聊天记录本，每说一句话，新的那句写在本子最后一行——前面的不会被擦掉。这就是聊天越聊越长的原因。

三、MyState(MessagesState) = "在国标表上加一栏"

你想在"聊天记录本"基础上，再多记一个"用户名"怎么办？写法就是：

class MyState(MessagesState): user_name: str

比喻：MessagesState 是国家标准表格（有"聊天记录"那一栏）；MyState 就是"在标准表后面，我自己补了一栏'用户名'"。

继承这两个字，在这里的意思就是：沿用标准表，再补一栏。一句话记住。

四、为什么一个用 @dataclass、一个用继承？（核心问题）

数据生活原型最省事的写法
AppContext（context）🪪 一张印好的工牌（进场定死，不可改）@dataclass：自动造卡片，填空即可
MyState（state）📋 一张要在国标表上加栏的白板继承：抄标准表，补一栏

两种数据长相不同，所以姿势不同：

工牌是卡片 → 看上面印的字用"点"：ctx.env（像翻到工牌上 env 那格）

白板是一张纸 → 按标签找用"方括号"：state['user_name']（像抽出写有 user_name 的便签）

这就是 43 课那个坑的根源：工具调用记录是"纸"（dict），模型请求是"卡片"（对象）。

五、一句话口诀（背这句就够）

📌 "卡片"用点（ctx.env）；"便签纸"用方括号（state['user_name']）。
📌 要造一张固定卡片 → 用 @dataclass；要在标准表上加栏 → 用 继承 MessagesState。
