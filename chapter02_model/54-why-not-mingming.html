54 · 第 2 轮改了 user_name=明明，回答为啥还是“小明”？

你的问题极精准，直接命中了 LangGraph 最反直觉的一个点。先给结论：

state 白板确实被改成了“明明”（实跑证明），但模型根本“看不到”白板这个键——它只看到消息列表。 第 2 轮你又说了句“不要调工具，直接答”，于是模型没调用 my_info，自然也没机会去读 state.user_name， 只能从聊天历史里已有的“小明”推答案，于是又答了“小明”。

一、实跑数据（54 demo 打印）

第 1 轮回答: 你叫小明。 第 1 轮后 state.user_name = 小明 第 2 轮回答: 你叫小明。 第 2 轮后 state.user_name = 明明 ← 白板确实被改写了！ 第 2 轮模型“看到了”的 messages： human: 我叫什么？ [AI]: [工具]: 白板用户名=小明 [AI]: 你叫小明。 human: 再汇报一次我是谁，不要调工具，直接答。 [AI]: 你叫小明。 ← 它照着历史里的“小明”复述

注意两件事同时为真：① 第 2 轮结束后 state.user_name 已经是“明明”（白板改成功了）； ② 但模型这一轮的回答是从上一条 AI 消息“你叫小明”复述来的——它从没去查新写的白板。

二、为什么模型“看不到” user_name？

这是 45/46 课“上下文工程”的终极回响：模型只有消息列表里给它的东西才知道。

自定义 state 键 user_name 只是存在 state 字典里的一个字段，它不会自动塞进发给 LLM 的 prompt。 唯一会去读它的，是那个工具 my_info（它在代码里写 runtime.state.get('user_name')）。

所以链路是这样的：

想让模型知道 user_name必须满足
靠白板（state.user_name）得有个东西把白板内容读出来再写进消息——也就是调 my_info 工具
第 2 轮用户下令“不要调工具”→ 工具没跑 → 没人把 user_name 写进上下文 → 模型只能看历史

三、那“明明”到底卡在哪一层？（人话比喻）

把 state 想成后台数据库，把 my_info 想成会查库的接口，把模型想成只看前台的客服。

你改了后台库里用户的名字（user_name=明明），但客服没调接口查库（你让他别调工具）， 他桌上只有之前的聊天记录写着“小明”，于是继续说“小明”。库里早改了，可客服不知道。

四、怎么让它答“明明”？两条路

路 ①：让模型调工具（撤销“不要调工具”）

把第 2 轮用户指令改成“汇报一下”，模型就会调 my_info → 工具读 state.user_name="明明" → 回答“明明”。

# 第 2 轮若允许调工具，工具会读到被改写后的白板： 白板用户名=明明 ← state 在合并输入时已变成 明明

路 ②：把身份放进会进 prompt 的地方

把当前身份写进 system_prompt，或在每次输入里把“我是明明”放进用户消息——这些会进 messages，模型就看到了。 自定义 state 键本身不进 prompt，这是设计使然。

五、一句话记住

📌 自定义 state 键只是后台数据，不会自动喂给模型；模型只认 messages。
📌 第 2 轮“你是小明”不是因为白板没改（白板已改明明），而是因为“不要调工具”导致没人把白板读出来放进上下文。
📌 想让新身份被模型采用：要么让工具读 state，要么把身份写进 prompt/消息。
